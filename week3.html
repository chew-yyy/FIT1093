00 / THE GOAL

What integrity and authenticity actually mean

  • Integrity (INT) — the data received was not modified in transit or storage.
  • Authenticity (AUTH) — the data received is not fabricated; it really came from the claimed sender.

The channel/storage is insecure: an attacker can turn message m into a tampered m'. We can't stop them touching it — so the strategy is to guarantee any tampering is detected.

Analogy · The wax seal The sender stamps a wax seal (a checksum) over the letter. If anyone opens or alters it, the seal breaks — the receiver notices. The trick that makes it unforgeable: the seal is computed with a secret key, so only legitimate users can produce a valid one. An attacker who edits the message can't recompute a matching seal.
01 / HASH FUNCTIONS

Hash functions — the building block

  • Input: message m of any length.
  • Output: digest h of short, fixed length L.
  • Always |m| >> |h| — it squeezes a lot down to a little.
  • No key — a plain hash takes only the message (that's the difference from a MAC later).

Memory aid Two properties to memorise: preimage resistance (can't go backwards) and collision resistance (can't find a twin). "Can't reverse it, can't clash it."
02 / PROPERTY 1

One-way security (preimage resistance)

Given a digest h = H(m), it is computationally infeasible to find the original m. Forward is efficient; backward is a wall.

m ──────► easy ──────► h = H(m) m ◄────── infeasible ◄────── h
Analogy · The blender Turning fruit into a smoothie is trivial; reconstructing the whole fruit from the smoothie is hopeless. A hash blends the message into a fixed-size purée you can't un-blend.

Why it matters: password storage (store H(password), not the password) and digital-signature security (later in the unit).

03 / PROPERTY 2

Collision resistance

It must be infeasible to find any pair of distinct messages m₁ ≠ m₂ with H(m₁) = H(m₂).

Why we need it Without it, an attacker finds two messages with the same digest, gets the honest sender to sign/MAC the harmless one, then swaps in the malicious twin — the tag still verifies. That's an undetectable modification attack.

Collisions must exist — the pigeonhole principle

Since |m| >> |h|, there are far more possible inputs than outputs, so collisions are unavoidable. With 10 inputs mapping into 9 possible hash values, once H(1)…H(9) fill all 9 slots, H(10) must land on one already taken.

Analogy · Pigeonhole principle 10 pigeons, 9 holes → at least two pigeons share a hole. For any hash, collisions exist; we can't remove them. The goal is only to make finding one take infeasibly long.
04 / BIRTHDAY ATTACK

The birthday paradox and the √ rule

Surprising fact: you only need about 23 ≈ √365 people in a room for a good chance that two share a birthday. Collisions appear far sooner than intuition suggests — because you're comparing every pair, not matching one fixed target.

The rule that carries the exam For a hash with n-bit output, an attacker finds a collision in about √(2ⁿ) = 2^(n/2) evaluations. Collision security is only half the output length.
n = 256-bit output ► collision findable in ≈ 2128 work ► so only secure against attacks with < 2128 ops // This is WHY modern hashes use 256+ bits: 2^128 must stay out of reach

Birthday-problem intuition: track the complement — the chance everyone is unique (364/365 × 363/365 × …). By 23 people it drops below 50%, so the chance of a shared birthday passes 50%.

05 / MAC

Message Authentication Codes (MAC)

A MAC is a keyed cryptographic checksum — a hash that also takes a secret key.

MAC tag T = C(K, M) • condenses a variable-length message M • using a SECRET key K • into a fixed-size tag / check code • many-to-one (like a hash) — but finding two messages with the same tag must be hard

How it's used

Sender computes T = C(K, M) and sends M ‖ T. Receiver recomputes C(K, M) with the shared K and compares. Match → accept; mismatch → reject.

The one security requirement: unforgeability

It must be infeasible for an attacker not knowing K to produce any new valid pair (M*, T*) where T* = C(K, M*) and M* was never MAC'd by the honest sender.

Unforgeability implies… (1) resistance to message-replacement (can't find another M with the same tag); (2) tags uniformly distributed (thwarts brute force); (3) the tag depends equally on all bits of the message (no weak spot).
Analogy · Hash vs MAC A plain hash is a public fingerprint — anyone can compute it, so anyone who edits the message can also recompute the fingerprint. A MAC is a fingerprint that needs your secret ink: without K, an attacker can edit the message but can't produce a matching tag.
06 / CONSTRUCTIONS

Building MACs: CMAC and HMAC

Two standard routes — from a block cipher, or from a hash function.

CMAC — from a block cipher

  • A CBC-based mode of operation designed for MAC (NIST, 2005).
  • Derives two subkeys K1, K2 from a single key K (K1 for full final block, K2 for a padded final block).
  • Works with any secure block cipher, e.g. AES-128.

HMAC — from a hash function

Hashes are fast and widely available, so we'd like a MAC built on one. But the naive KeyedHash = Hash(K ‖ m) has weaknesses (length-extension). The fix is the nested HMAC standard (RFC 2104):

HMAC(K, M) = Hash[ (K⁺ ⊕ opad) ‖ Hash[ (K⁺ ⊕ ipad) ‖ M ] ] K⁺ = key padded out to block size ipad,opad = fixed padding constants (inner / outer) // overhead ≈ hashing just 3 extra blocks vs hashing M alone
  • Any hash can plug in — MD5 / SHA-1 / RIPEMD-160 (obsolete), SHA-2 / SHA-3 (recommended).
Memory aid CMAC → Cipher (CBC). HMAC → Hash (nested, two pads). Naive Hash(K‖m) is not safe — that's the whole reason HMAC exists.
07 / CONF + INT

Combining confidentiality with integrity

Real secure communication needs both confidentiality (encryption) and integrity (MAC) — encryption alone doesn't stop tampering.

  • Combine authentication + encryption, e.g. encrypt-then-MAC.
  • Use separate keys for encryption and MAC to avoid cross-interactions.
  • Do it carefully so neither mechanism's security is weakened.
In practice Use a purpose-built Authenticated Encryption (AE) mode that does both at once — e.g. GCM (NIST, 2007). It gives confidentiality + integrity efficiently in one construction, which is why TLS uses AES-GCM.

Reference: Stallings & Brown, Computer Security: Principles and Practice (Ch. 2.2, Ch. 21.1–21.2).
