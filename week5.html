00 / THE SETUP

The problem public-key crypto exists to solve

In Symmetric Key Encryption (SKE) both sides encrypt and decrypt with the same secret key K. That's fast — but it raises one nasty question: how do you get that shared secret to the other person in the first place, when the only channel you have is a public one an attacker can read? This is the key distribution problem.

Analogy · The locked-box paradox You want to post someone a locked box, but the only copy of the key… is inside the box. SKE has this exact chicken-and-egg problem: to send data securely you already need a shared secret, but sharing that secret securely is the whole problem. Public-key crypto is the way out.

Diffie–Hellman (1976) was the first idea suggesting Public-Key Cryptography (PKC): jointly compute a shared secret out of public values only, so no secret ever travels down the channel.

Historical footnote for exam trivia: DH was secretly discovered by Malcolm Williamson (UK GCHQ) in 1974, two years before the public version.

01 / KEY EXCHANGE

Diffie–Hellman Key Exchange

DH lets Alice and Bob agree on a shared secret over a public channel. It's everywhere: TLS/HTTPS, IPsec, Bluetooth, 5G, IoT.

The moving parts

  • p and g — public parameters, p is a large prime.
  • a = Alice's private key  ·  b = Bob's private key.
  • A = Alice's public key = ga mod p  ·  B = gb mod p.
  • Shared secret K — computed independently by both, never sent.

Alice

private a
A = ga mod p
K = Ba mod p
→
send A
←
send B

Bob

private b
B = gb mod p
K = Ab mod p

Why they land on the same K

Alice: K = Ba = (gb)a = gba mod p Bob: K = Ab = (ga)b = gab mod p // ba = ab, so both get the SAME secret via different routes
Analogy · Mixing paint Start with a public base colour everyone can see (g, p). Each person stirs in their own secret colour and posts the mixture (A, B) publicly. Each then stirs their own secret colour into the mixture they received. Both bowls end up the identical shade (K). An eavesdropper sees the public mixtures but separating a mixed paint back into its ingredients is practically impossible — that's the one-way trick doing the work.
Memory aid “Same secret, opposite order.” Alice does gb then raises to a; Bob does ga then raises to b. Exponents commute → same K. The only thing that must stay private is your own exponent (a or b).

Worked example (from the slides)

g public, p = 23, a = 6 (Alice), b = 15 (Bob) A = 8 B = 19 (the public keys exchanged) Alice: K = 196 mod 23 = (361)3 = 163 = 2 (mod 23) Bob: K = 815 mod 23 = 2 (mod 23) ✓ match

Exam tip: reduce after each multiplication (e.g. 19² = 361 → 16 mod 23) so the numbers never blow up. That's exactly what "efficiently computable" means in practice.

02 / DH SECURITY

What keeps Diffie–Hellman safe (and what breaks it)

To recover K, an attacker needs a or b. Two hard problems stand in the way:

ProblemAttacker knowsWantsStatus
Discrete Log Problem (DLP) p, g, A where A = ga the exponent a Infeasible (large p)
Diffie–Hellman Problem (DHP) p, g, A, B K = gab directly Infeasible (large p)
Memory aid Easy one way, hard the other. Computing A = ga mod p is fast (repeated squaring). Going backwards — finding a from A — is the discrete log, and it's the wall attackers hit.

The catch: Man-in-the-Middle (MITM)

DH proves nobody can compute the secret from the public values — but it says nothing about whose public key you actually received. If an attacker swaps B for their own M = gm, the whole thing collapses.

Alice ──A──► Attacker ──M──► Bob Alice ◄──M── Attacker ◄──B── Bob Attacker sets up TWO shared keys: K1 = Am (shared with Alice) K2 = Bm (shared with Bob) Then relays: E(m,K1) → Decrypt(K1) → re-encrypt E(m,K2) → Bob // Attacker reads/edits everything; both sides think they're secure
Attack · Integrity failure MITM is an integrity attack on the public-key value. DH gives you confidentiality of the maths but no authentication of who's on the other end. The fix comes later in the unit: authenticated certificates / digital signatures.
Analogy · The dishonest courier Picture the paint mixtures being hand-delivered by a courier who quietly swaps in his own tins going each way. Alice and Bob each mix a "shared" colour — but with the courier, not each other. He sits in the middle repainting every message.
03 / ELGAMAL

ElGamal PKE — turning DH into encryption

DH is a key exchange (both sides must be online, both publish keys). ElGamal (1985) converts it into public-key encryption: only the receiver Bob publishes a long-term key, and Alice can encrypt to him whenever she likes.

The trick: Alice generates a fresh ephemeral (one-time) DH keypair a/A per message, derives the DH shared key with Bob, encrypts the message with it, and ships A alongside the ciphertext so Bob can reconstruct the same key.

Alice (sender)

look up Bob's B
pick ephemeral a
A = ga mod p
K = Ba = gab mod p
C = Enc(K, P)
→
send
A, C

Bob (receiver)

private b, public B
K = Ab = gab mod p
P = Dec(K, C)
Memory aid ElGamal = DH + a note attached. "A, C" — the ephemeral public key rides with the ciphertext. Ephemeral = new random a every message, which is why the same plaintext encrypts differently each time.

Note "Enc" here is a symmetric cipher keyed by the DH-derived K — so ElGamal is already quietly doing the hybrid trick you'll meet at the end.

04 / RSA

RSA PKE — the first public-key cipher (1977)

Rivest, Shamir, Adleman. (Secretly found earlier by Clifford Cocks, GCHQ, 1973.) Unlike DH/ElGamal, RSA's security rests on factoring, not discrete logs.

KeyGen

1. pick two distinct large primes p, q 2. modulus n = p × q 3. Euler totient φ(n) = (p−1)(q−1) 4. pick e coprime to φ(n) → public key = (e, n) 5. d = e−1 mod φ(n) → private key = d // so that e × d ≡ 1 (mod φ(n)) — d "undoes" e

Encrypt / Decrypt (both just modular exponentiation)

Encrypt: C = me mod n // with the PUBLIC key Decrypt: m = Cd mod n // with the PRIVATE key
Analogy · A box of open padlocks Bob mass-produces open padlocks and hands them out freely — that's his public key (e, n). Anyone can snap a message shut inside a box. But only Bob holds the key (d) that opens them. Distributing the padlock reveals nothing about the key.

Worked example (p = 5, q = 11)

KeyGen n = 5 × 11 = 55 ; φ(n) = 4 × 10 = 40 pick e = 3, then d = 27 since (3 × 27) mod 40 = 81 mod 40 = 1 ✓ public (3, 55) private (27, 55) Encrypt m = 13 C = 133 mod 55 = (169 mod 55) × 13 mod 55 = 4 × 13 = 52 Decrypt C = 52 m = 5227 mod 55 = … = 13 ✓
Memory aid · don't mix up the keys Public = (e, n) · e for encrypt/everyone. Private = d · d for decrypt. And e × d ≡ 1 (mod φ(n)) is the linchpin — d is just e's inverse mod φ(n).
05 / RSA PROOF

Why RSA decryption always recovers m

It comes straight out of number theory — one theorem does all the work:

Euler's Theorem If n = p×q and e × d ≡ 1 (mod φ(n)), then for any M:   Me×d mod n = M.
Decrypt(C) = Cd mod n = (me)d mod n = me×d mod n = m // by Euler's Theorem, since e×d ≡ 1 mod φ(n)
One-line intuition Encrypting raises m to e; decrypting raises to d. Because e and d are inverses mod φ(n), the two exponentiations cancel out and you're back to m.

RSA security — what the attacker faces

The secrets are d, φ(n), p, q. To decrypt without permission, an attacker would:

  • Brute-force all n possible messages — hopeless for large n; or
  • Compute d = e−1 mod φ(n) — but that needs φ(n) = (p−1)(q−1), which needs p and q…
  • …i.e. factor n — the Integer Factorisation Problem, infeasible for large n.

Legitimate users only ever do exponentiation (easy); the attacker is forced into factoring (hard). That asymmetry is the whole security argument.

07 / INTEGRITY

Integrity of the key directory → certificates

PKE removes the distribution problem, but a new one appears: are you sure the public key you looked up really belongs to Bob? If an attacker replaces Bob's pkR with their own pkA in the directory, Alice encrypts to the attacker while believing it's Bob. This is the same devastating integrity attack as DH's MITM.

Solution · Digital certificates A trusted Certification Authority (CA) vouches for the binding "this public key belongs to Bob" by signing it. Anyone can verify the certificate with the CA's public key to confirm the pk is authentic — like a tamper-proof government seal on an ID. This blocks MITM/integrity attacks. 08 / PUTTING IT TOGETHER

PKE vs SKE, and why we use both (Hybrid Encryption)

PKE (public-key)SKE (symmetric)
Keys Each user has pk & sk, mathematically related Two users share one secret key k
Do / undo Do with pk, undo with sk Do & undo with the same k
Distribution No key-distribution problem Has key-distribution problem
Speed Slower Faster

Neither wins outright — so combine their best features. That's Hybrid Encryption (a.k.a. the Digital Envelope):

  • Use PKE to transport a small, random symmetric key → solves key distribution; slowness doesn't matter because the key is tiny.
  • Use SKE under that key to encrypt the actual (possibly huge) message → fast bulk encryption.
Sender builds the "envelope" 1. generate random symmetric key k 2. encrypted message = Enc_SKE(k, message) // fast 3. encrypted key = Enc_PKE(receiver_pk, k) // small digital envelope = { encrypted message + encrypted key } Receiver opens it 4. k = Dec_PKE(receiver_sk, encrypted key) 5. message = Dec_SKE(k, encrypted message)
Analogy · Armoured truck for the key only Sending a whole warehouse of goods by slow armoured truck (PKE) would take forever. Instead you use the truck to deliver just one small house key, then move all the goods quickly through the normal door that key opens (SKE). PKE secures the key; SKE moves the data.
This is how the real world works TLS, PGP/encrypted email, Signal, etc. are all hybrid: public-key crypto to establish/transport a session key, symmetric crypto for the traffic.
